# 第三方平台经营技术设计方案

> 日期：2026-11-15  
> 状态：待审阅；本文为设计，不代表代码已实现或测试已通过。

## 1. 目标与范围

在管理后台新增“第三方平台”一级菜单及房态日历、平台订单、经营统计、平台与主播设置四个二级页面。管理员手动录入其他平台订单，以房间和日期查看订单，按日期、平台、主播、房间计算营业额、手续费、间夜、订单数和净利润。

第一阶段独立保存和统计第三方订单；不读取、修改小程序订单来判断房态，不联动支付、清洁、现有入住退房，不做全店汇总、不导入桌面版历史数据，不处理提前退房或退款。新模块的房态不代表全渠道可售房态，界面明确提示。日历和报表参考桌面版住宿日期口径，不意味着移植桌面版的备份、清空、默认费率、客人证件等所有功能。

## 3. 菜单和用户流程

```text
第三方平台
├─ 房态日历：日 / 周 / 月，显示房间、订单状态、平台；空格可带入房间和日期录单
├─ 平台订单：列表筛选、创建、编辑、状态流转、查看详情
├─ 经营统计：总览、每日、平台、主播、房间维度
└─ 平台与主播设置：列表、新增、编辑、启停
```

房态格子表示当晚，日期区间左闭右开。月视图每房每日期一格并允许横向滚动，周从周一开始；切换前后周期和回到今天。日历显示 `BOOKED`、`CHECKED_IN`、`CHECKED_OUT`，排除 `CANCELLED`。由于本期不处理提前退房，同一房间的有效订单计划日期不得重叠。点击订单进入详情；空格进入预填房间和当天入住、次日退房的新增表单。

订单创建输入平台、可选主播、房间、入住/退房日期、入住人数、成交总额、手动手续费和可选平台订单号/备注。系统显示计算得到的间夜和净利润。修改时重新验证日期、引用和冲突；状态变更通过独立操作完成。推荐状态：`BOOKED → CHECKED_IN → CHECKED_OUT`，`BOOKED → CANCELLED`；其他跳转拒绝，重复提交不得创建重复变更。订单按状态筛选，并支持日期、平台、主播、房间和订单号查询；日历与列表只显示第三方平台订单。

## 4. 模块边界和数据流

新增 `backend/src/main/java/com/homestay/module/external/`，控制器只做参数绑定、权限和响应；服务负责事务、校验、状态和分摊；Mapper 负责 SQL；请求 DTO、响应 VO、持久化实体分离。后台复用 `Result`、`PageResult`、`BusinessException`。金额用 `BigDecimal` 与数据库 `DECIMAL`，统计时转换为整数分以精确分摊。

```text
管理后台 → external API → external controller → external service → external mapper → 三张新表
                                                        └→ 只读房间信息
```

不调用现有订单、支付、清洁服务；不写房间状态。对房间的依赖限制为房间标识、名称和必要的存在性/锁定检查。平台与主播历史可通过停用保留，不提供物理删除。

## 5. 数据库设计

新增 `backend/sql/migrations/20261115_external_platform.sql`；新装数据库同时更新 `backend/sql/homestay_db.sql` 的建表部分，不能执行该初始化脚本升级已有数据库。既有 `room`、`booking_order`、`payment_record`、`operating_expenses` 结构不变、不回填。三张表统一 `utf8mb4`、InnoDB，时间使用现有 `create_time` / `update_time` 风格。字段及约束为建议的最终设计，实施前须与目标库实际 schema 核对。

### 5.1 `external_platform`（新增）

| 字段 | 类型 | 空 / 默认 | 说明 |
|---|---|---|---|
| id | BIGINT | 非空，自增 | 主键 |
| name | VARCHAR(50) | 非空 | 平台名称，去首尾空格后唯一 |
| status | TINYINT | 非空，1 | 1 启用、0 停用 |
| create_time | DATETIME | 非空，当前时间 | 创建时间 |
| update_time | DATETIME | 非空，当前时间并更新 | 修改时间 |

初始数据建议为抖音、美团、携程、飞猪；使用唯一名称和幂等插入，避免升级重复。无默认费率字段，手续费每单手填。

### 5.2 `external_anchor`（新增）

| 字段 | 类型 | 空 / 默认 | 说明 |
|---|---|---|---|
| id | BIGINT | 非空，自增 | 主键 |
| name | VARCHAR(50) | 非空 | 主播名称，允许同名，以 ID 区分 |
| status | TINYINT | 非空，1 | 1 启用、0 停用 |
| remark | VARCHAR(255) | 可空 | 备注，可用于区分同名主播 |
| create_time | DATETIME | 非空，当前时间 | 创建时间 |
| update_time | DATETIME | 非空，当前时间并更新 | 修改时间 |

### 5.3 `external_order`（新增）

| 字段 | 类型 | 空 / 默认 | 说明 |
|---|---|---|---|
| id | BIGINT | 非空，自增 | 主键 |
| order_no | VARCHAR(50) | 非空 | 内部订单号，唯一 |
| platform_order_no | VARCHAR(100) | 可空 | 平台订单号；空字符串统一转 NULL |
| platform_id | BIGINT | 非空 | 平台 ID |
| anchor_id | BIGINT | 可空 | 主播 ID；无主播为空 |
| room_id | BIGINT | 非空 | 现有 room.id |
| check_in_date | DATE | 非空 | 计划入住日期，含该夜 |
| check_out_date | DATE | 非空 | 计划退房日期，不含该夜 |
| guest_count | INT | 非空 | 入住人数，大于 0 |
| total_amount | DECIMAL(12,2) | 非空 | 用户付款总额，元，非负 |
| platform_fee | DECIMAL(12,2) | 非空，0 | 手工平台手续费，元，非负 |
| anchor_fee | DECIMAL(12,2) | 非空，0 | 手工主播手续费，元，非负；无主播须为 0 |
| status | VARCHAR(20) | 非空，BOOKED | BOOKED、CHECKED_IN、CHECKED_OUT、CANCELLED |
| remark | VARCHAR(255) | 可空 | 备注 |
| create_time | DATETIME | 非空，当前时间 | 录入时间 |
| update_time | DATETIME | 非空，当前时间并更新 | 修改时间 |

不保存冗余间夜和净利润；不增加实际退房、费率、入住人、退款或统计表。金额范围按 DECIMAL(12,2) 校验，两位小数；如费用合计超过成交额，允许负净利润（不强加尚未确认的限制）。日期要求退房晚于入住。状态保存后仅通过状态接口变更，不开放物理删除。

索引：`UNIQUE(order_no)`、`UNIQUE(platform_id, platform_order_no)`（NULL 允许多条）、`(room_id, status, check_in_date, check_out_date)`、`(platform_id, check_in_date)`、`(anchor_id, check_in_date)`。名称唯一的排序规则及大小写行为在迁移前确认。平台与主播采用受限引用并通过启停保留；房间逻辑删除不会触发物理外键，历史展示按 room ID 左关联读取包括 deleted=1 的记录并标记已删除，不通过默认过滤删除记录的服务查询。房间号被修改后历史显示当前房间号；是否需要历史名称快照列为待审阅事项，不隐式添加第四张表或额外字段。若物理删除已有房间，历史无法解析的情况显示“已删除房间（ID）”，不丢失订单统计。

并发冲突：第三方订单创建、改房改期在同一事务内对目标 room 行按固定 ID 顺序 `SELECT ... FOR UPDATE`，再以 `existing.check_in_date < new.check_out_date AND existing.check_out_date > new.check_in_date` 检查非取消订单（更新排除自身），成功后写入；改房涉及两间时按 ID 顺序锁，失败回滚。事务隔离与当前读需以 MySQL 集成测试验证。此锁只序列化新模块使用该约定的写入，不保证与小程序互斥，符合本期边界。

## 6. API 设计

公共前缀 `/api` 来自现有应用 context-path，以下路径省略 `/api`。新增接口使用现有 `Result<T>`；分页用 `PageResult<T>`。时间参数使用 `yyyy-MM-dd`，金额最多两位小数；校验失败返回业务错误，按现有全局异常处理器的实际约定映射 code/HTTP 状态，不假设两者相同。所有接口服务端验证 employee + owner（建议权限）；菜单隐藏不是授权。输入 ID 不存在、停用选择、状态不合法及冲突均返回明确错误，不泄露 SQL。

| 方法和路径 | 操作 | 主要请求与响应 |
|---|---|---|
| GET `/external/platforms` | 新增 | `includeDisabled`；返回 ID、名称、状态，用于设置和选择 |
| POST `/external/platforms` | 新增 | `name`；返回新 ID |
| PUT `/external/platforms/{id}` | 新增 | `name,status`；更新名称或启停 |
| GET `/external/anchors` | 新增 | `includeDisabled`；返回 ID、名称、状态、备注 |
| POST `/external/anchors` | 新增 | `name,remark`；返回新 ID |
| PUT `/external/anchors/{id}` | 新增 | `name,remark,status` |
| GET `/external/orders` | 新增 | `page,size,startDate,endDate,platformId,anchorId,roomId,status,keyword`；分页返回订单和计算结果；日期筛选按住宿区间与查询区间重叠 |
| GET `/external/orders/{id}` | 新增 | 返回单笔订单、引用显示名、间夜和净利润 |
| POST `/external/orders` | 新增 | 提交订单录入字段；状态初始 BOOKED，返回 ID |
| PUT `/external/orders/{id}` | 新增 | 提交可编辑字段；不得直接传 status，校验冲突及状态 |
| POST `/external/orders/{id}/status` | 新增 | `status` 为目标状态，验证状态流转并并发保护 |
| GET `/external/calendar` | 新增 | `startDate,endDate,platformId`，结束日期含当天；返回房间和日期覆盖的订单列表，前端生成日期格；限制最大查询范围 |
| GET `/external/statistics` | 新增 | `startDate,endDate`（均含当日，可选平台、主播、房间）；返回总览、每日和按平台/主播/房间分组，含订单数、间夜、各金额 |
| GET `/room/list` | 保持不变 | 现有房间选择接口，不增加第三方条件 |

平台/主播更新时不能选择新停用对象；编辑既有订单允许保留原先已停用的引用。平台唯一冲突和同平台订单号冲突由数据库唯一索引兜底并转业务错误。列表分页限制大小，统计和日历的日期范围上限由实现配置并在接口文档声明。无新增导出接口：Excel 导出仅为先前建议，尚未作为本期明确要求。

## 7. 统计规则与示例

1. 时间按 Asia/Shanghai 的自然日期；只统计 `CHECKED_IN`、`CHECKED_OUT`，`BOOKED` 只展示日历、`CANCELLED` 排除。
2. 一笔订单总金额、平台手续费、主播手续费分别按完整计划间夜平均分配到每晚。先转换整数分，整数除法的余数从入住日起逐晚加一分。金额、手续费分别分摊；每晚净利润是三项差额，支持负数。所有晚合计严格还原整单。
3. 查询选定区间只取属于区间内的住宿夜；间夜为匹配房晚数；每日订单数按当日去重；整个查询区间及各维度订单数按订单 ID 去重。跨月订单可能各月各计一单，月订单数不可相加替代跨月去重。
4. `total_amount` 为营业额，净利润 = 营业额 − 平台手续费 − 主播手续费；不扣经营支出，不推断实际收款或退款。主播为空归入“无主播”；不同维度为同一订单的不同投影，不能相加。
5. 例：5 月 30 日入住、6 月 2 日退房，成交 1000.00、平台费 100.00、主播费 0。每晚成交分别 333.34、333.33、333.33；平台费分别 33.34、33.33、33.33。5 月计 2 晚、666.67 元、平台费 66.67 元；6 月计 1 晚、333.33 元、平台费 33.33 元。订单在两月分别计一单，跨月统计去重为一单。

## 9. 实施步骤和验收

1. **数据库**：编写增量及初始化脚本；验收新库和已有库均能得到三张表及四个平台，已有表与数据不变；唯一约束有效，重复执行增量行为经验证。
2. **目录及权限**：完成平台、主播维护与服务端 owner 检查；验收启停和同名主播区分有效，未登录、宾客、非 owner 不可访问。
3. **订单与冲突**：完成创建、修改、列表、状态流转、房间只读及事务锁；验收日期相邻可保存，重叠拒绝，并发争抢仅一笔成功，取消后允许重订。
4. **日历及统计**：完成查询和整数分分摊；验收周/月切换、跨月、每日/多维去重、余分归属、无主播及负利润结果正确。
5. **后台接入**：添加菜单、路由、四页及错误/加载状态；验收第三方订单可从日历录入并查看，功能仅出现于新增菜单，标注不代表小程序房态。
6. **回归与发布验证**：执行第 10 节检查，记录结果；检查实际部署库的升级和回滚流程。

## 11. 发布与风险

- 发布前备份目标库并检查三张表名、初始平台及权限。先在隔离库验证增量 SQL；已有卷不会自动运行初始化脚本。先部署表结构，再部署兼容应用，验证后开放菜单。
- 回滚应用可先移除菜单并回退代码；新表默认保留以保护已录数据。只有完成数据导出、核对并明确授权后才考虑删除新表；不要以初始化脚本重建数据库。
- 第三方日历不代表全渠道库存，不能防止与小程序或外部平台之间超卖。
- 当前房间支持逻辑删除；历史查询须覆盖已删除房间。历史房号跟随现有房号修改是本方案假设。
- 订单/主播/平台名称可能修改，历史报表按当前名称显示；如需名称快照需另行确定。
- 建议所有页面和接口仅 owner 使用；这一权限为参考现有经营支出功能的设计建议，需在审阅时确认。现有授权拦截器仅验证 JWT，不能依赖前端菜单保护接口。
- 当前订单设计只记录入住人数，不记录入住人身份、不处理退款；后续扩展需重新评估数据和统计口径。
